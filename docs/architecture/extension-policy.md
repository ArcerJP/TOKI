# Extension policy

構造の追加は、現状で置き場がない責務に限定する。大量の空フォルダや将来用の抽象化を先に作らない。

1. **分類**：実装、正式仕様、判断、原本、派生知識、作業記録、短期メモ、手順のどれか。
2. **既存適合**：[directory-map](directory-map.md) の既存の置き場で足りるか確認。
3. **責務と正本**：1行で目的・責任範囲・更新者を説明し、[source-of-truth](source-of-truth.md) に重複がないか確認。
4. **ライフサイクル**：作成・更新・失効・終了の条件を定める。
5. **公開範囲**：個人情報・秘密・原本の公開可否を確認し、必要なら書込前に除外規則を追加。
6. **文脈量**：ルートAGENTSへ本文を増やさず、必要時のリンクを追加。下位AGENTSはその領域に固有の規則がある場合だけ。
7. **手順の再利用**：繰り返す作業にのみSkillを追加。説明文で発動条件を明確にし、重複・万能Skillを避ける。
8. **互換性と検証**：既存アプリ・公開範囲・CIへの影響を調べ、適切な検証を行う。
9. **記録**：directory-map、関連索引、必要ならADRを更新する。

作業は [WORKFLOW](../../work/WORKFLOW.md) のリスクで判断する。構造・認可・公開範囲などの重要な変更はL3として、人の承認を確認する。同じ依頼内ですでに承認された範囲を再承認する必要はない。

Git ignoreは秘密保護の完全な仕組みではなく、既に追跡済みのファイルには効かない。追加時は `git check-ignore` とstaged diffの両方を検証する。公開配信への追加は別の明示的な変更として扱う。根拠：[Git公式のgitignore仕様](https://git-scm.com/docs/gitignore)（2026-10-15確認）。改行設定は [gitattributes](https://git-scm.com/docs/gitattributes) に従い、既存vendorの例外を維持する。
