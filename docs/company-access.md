# 会社・団体ごとのアクセス管理

## 利用者の流れ

1. 会社URL、または会社コードからGoogleでログイン。
2. 管理者にメールアドレスを招待登録されていれば参加可能。未招待なら会社コードで参加申請し、管理者の承認を待つ。
3. 参加済みの会社を選んで開く。
4. 初回は全グループ・未所属が非表示。「表示グループ」で必要な行を選択する。

再起動時はログイン状態・会社のアクセス権・前回選択した会社の予定を確認する。確認中は簡潔な読み込み表示とし、取得できれば会社選択画面を挟まず予定表を開く。未ログイン、会社の選択が必要、復元失敗の場合は既存のログイン・会社選択・エラー画面を表示する。オフライン閲覧の条件と認可確認は変更しない。

会社URL・会社コードは参加先を指定するための情報であり、予定の閲覧権限そのものではない。社内の承認済みメンバーは全グループの閲覧・編集が可能。表示選択はアクセス制御ではなく、PC・スマートフォン共通の個人設定。

管理者は、PC・スマートフォンのアカウントアイコンから「会社・アカウント」を開き、申請承認、招待登録、招待取消、アクセス停止、管理者変更を行う。管理項目は現在の団体の管理者にだけ表示する。招待登録はメールを送信しない。会社URLを本人へ別途伝える。招待は7日間、期限切れは再登録。停止した人は、コードの再入力や招待登録だけでは再参加できず、管理者の「参加を再許可」が必要。最後の管理者は停止・一般メンバーへの変更ができない。

### 管理者権限の引き継ぎ

1. アカウントアイコンを押し、「管理者権限の譲渡」で相手を選択する。
2. 「譲渡内容を確認」で団体名、相手のメールアドレス、自分が一般メンバーになることを確認する。
3. 「譲渡を確定」を押す。成功すると相手は管理者、自分は一般メンバーとなり、管理項目は非表示になる。

選択できるのは同じ団体の承認済みメンバー（自分以外）。未参加の相手は先に招待・参加承認を行い、本人のGoogleログイン後にアカウント画面を開き直す。停止中・承認待ち・別団体だけに所属する人への譲渡はできない。サーバーでも相手の有効なGoogleアカウントと所属を再検証する。

相手の昇格と自分の降格は、団体単位のロックと1回のトランザクションで確定する。途中で失敗した場合は両方とも変更しない。予定、所属、他の管理者、他の団体での権限は変更しない。これは団体の管理権限だけの譲渡であり、アプリ運営者のSupabase権限は対象外。通信中断で結果が不明な場合は、アカウント画面を開き直して現在の権限を確認する。

未承認の参加申請は7日間で期限切れ。期限切れは一覧から外し、次の申請・管理画面の取得時に整理する。申請が混み合っている場合、管理者はメールアドレスで招待登録できる。招待済みの人は通常どおりログイン・会社コード入力で参加でき、申請枠の空きを待つ必要はない。

会社への参加アカウントと、予定表上の「人」の行は別。承認時に行を勝手に追加せず、既存の人・予定は維持する。

### アクセス停止済みの参加者を削除する

管理者は、参加者の「アクセスを停止」を実行した後に表示される「団体から削除」で、その団体の所属記録を削除できる。削除前に対象メールアドレスと影響を確認する。承認待ち・利用中の人は直接削除できない。確認中に別の管理者が参加を再許可した場合も、サーバーが最新の状態を確認して削除を拒否する。

削除した人は参加者一覧から消え、アクセス停止の記録と、その団体からの本人宛ての未使用招待も削除する。再参加には改めて招待・承認が必要で、以前の管理者権限は自動復元しない。削除は停止の継続ではないため、本人は会社コードで再び参加申請できる。

Googleアカウント・TOKIへのログイン・他団体の所属・予定表の人の行・可能時間・MTGは削除しない。オフライン端末に保存済みのコピーを即時消去できない制約も変わらない。通信が途切れて結果が不明な場合は、アカウント画面を開き直して参加者一覧を確認する。

## 新しい会社・団体の作成

一般利用者・会社管理者からの会社作成はAPIで拒否する。新規作成はSupabaseプロジェクトを管理する運営者だけがSQL Editorで行う。

```sql
select toki_private.provision_company('会社・団体名','初期管理者のGoogleメールアドレス');
```

返された会社コードを初期管理者に伝える。実行ごとに空の会社を1つ作成するため、同じ依頼を二重実行しない。初期管理者の招待は30日間。メールアドレスを含めた実行用SQLはGitに保存しない。

## 初期設定・移行の順序

認証設定が完了する前に本番へ新しい画面を公開しない。

1. Google Cloudの既存Web OAuthクライアントに、SupabaseのGoogle設定画面に表示されるCallback URLを「承認済みのリダイレクトURI」として追加。既存のJavaScript生成元は残す。
2. Supabase → Authentication → Sign In / Providers → Googleを有効化。WebクライアントIDと対応するクライアントシークレットを登録。「Skip nonce checks」「Allow users without an email」は無効のままにする。シークレットはSupabaseの設定画面だけに入力し、Gitやチャットへ貼らない。
3. Supabase → Authentication → URL ConfigurationでSite URLとRedirect URLsを実際のTOKI公開URLに設定。不要なワイルドカードは使わない。Email、匿名ログイン、その他のプロバイダーは無効にし、Googleのみを許可する。
4. `database/schema.sql`、続いて`database/companies.sql`をSQL Editorで適用。後者は旧共有URLのAPI権限を取り消す。この時点から旧画面は共有予定へ接続できないため、公開更新と続けて行う。
5. 同じSQL Editorで、移行対象と確認済みの初期管理者を指定する。

   ```sql
   select toki_private.bootstrap_company(
     '既存の予定表ID', '会社・団体名', '初期管理者のGoogleメールアドレス'
   );
   ```

   既存の予定表に会社を関連付け、既存データをコピー・変更しない。会社コードはサーバーで自動生成。初期管理者の招待は30日間。管理者の個人情報を埋め込んだSQLはリポジトリへ保存しない。
6. 新しい静的ファイルを公開。初期管理者が指定したGoogleアカウントでログインし、管理者表示と既存予定を確認する。
7. 管理者が必要な人を招待、または参加申請を承認する。Googleのアプリがテスト中なら、対象者をGoogle Cloudのテストユーザーにも追加する。

認証用のGoogleスコープは本人確認のみ。任意のカレンダー取り込みは従来のGoogle Identity Servicesで別途許可を取得する。会社にログインしただけではGoogleカレンダーを取得しない。

## データと権限

- `toki_private.companies`：会社名・会社コード・予定表ID。
- `toki_private.company_members`：GoogleアカウントのユーザーID、会社、権限、参加状態。
- `toki_private.company_invites`：会社、招待先メール、有効期限。
- 公開RPC `toki_company`：Google認証履歴、現在有効なSupabaseセッション、確認済みメール、現在の会社所属を毎回検証。会社IDを直接指定しても、未所属・承認待ち・停止中の読み書きは拒否する。
- 管理操作はその会社の管理者だけ。管理者権限を招待パラメーターで取得できない。会社コードで自分を承認することもできない。
- テーブルへのAPI直接アクセス、旧 `toki_share` とその内部関数は無効。旧スキーマを再実行しても会社移行後は旧APIを再開しない。
- 保存は版番号を照合し、同時編集時の上書きを防止。
- 会社作成は非公開の運営者用関数だけ。会社の管理者に運営者権限は与えない。
- RPCはアカウント停止・セッションの期限も確認。失敗したリクエストを含め、1アカウント・1分あたり読み取り120回、保存60回、管理操作30回、参加申請5回で制限する。制限時はHTTP 429を返し、画面側も1分待つ。DB内の回数記録は各アカウント最大4行。
- 参加申請待ちは1人5社、1社50人、期限7日間。新しい未招待の申請は会社全体で10分30回・24時間200回まで（失敗も含む）。既存の申請の再送や、招待済みの人はこの会社単位の回数に含めない。各アカウントの回数制限は引き続き適用する。
- 会社の承認済みメンバーは500人まで。申請待ち・停止中の記録は別枠とし、停止した人のアクセス禁止は維持する。招待記録は期限切れを含め100件まで。満員の会社からの招待があっても、ほかの参加済み会社を開ける。期限切れの招待は管理画面から取り消せる。
- 予定表は2 MiBまで。使用するフィールドだけを許可し、件数・参照先・日付・時刻・文字数をサーバーで検証する。拒否した保存は版番号もデータも変更しない。
- 人名・グループ名はNFKC正規化、ECMAScriptの空白規則、C0/C1制御文字の禁止で検証する。重複比較はUnicode小文字化とギリシャ語の最終シグマの統一を使用。DBと画面はUnicode 16.0の同じ対応表・定義済み文字範囲を使用し、環境ごとの大小文字判定の違いを避ける。それ以降の新規文字・未定義文字・不正なサロゲートは保存しない。PostgreSQL 17の正規化に未収録の囲み英数字36文字（U+1CCD6〜U+1CCF9）も両側で事前変換する。対応表はUnicode 16.0対応のNodeで `scripts/generate-name-rules.cjs` を実行して両方まとめて生成し、展開する大文字İも扱う。Unicodeを更新するときはDBと画面の両方を検証する。空白・互換文字・大小文字を照合する回帰テストを実行する。

## ブラウザー・公開経路の保護

CSPでスクリプト・通信先をTOKI、Supabase、Googleの必要な経路へ制限。任意のインラインスクリプト、eval、外部フォーム送信、プラグイン埋め込みを禁止する。表示文字列はHTMLとして解釈せずtextContent等で設定する。Googleカレンダーの認証待ち中にログアウトした場合、遅れて届く認証結果も破棄する。

GitHub Pagesでは独自のレスポンスヘッダーを設定できないため、埋め込み画面ではUIを非表示にする補助策を使用。ヘッダーの`frame-ancestors 'none'`と同等の保護ではない。独自ドメイン・ヘッダー設定可能なホスティングへ移る場合は、CSPのレスポンスヘッダーと`frame-ancestors 'none'`も設定する。同じ`arcerjp.github.io`の他アプリとはブラウザーのオリジンを共有するため、会社向けの運用ではTOKI専用ドメインへの分離を推奨する。

GitHub ActionsはコミットSHAで固定し、依存関係の監査と全テストが成功した場合だけ公開する。検証ジョブには公開権限を与えず、デプロイジョブに限定する。公開対象は静的ファイルの許可リストのみ。

アプリ内の回数制限は、ネットワーク帯域を埋めるDDoSや大量のGoogleアカウント作成を防ぐWAFの代替ではない。Supabase・GitHub側の障害やアカウント侵害は別途対策が必要。運営者のGoogle・GitHub・Supabaseアカウントは多要素認証で保護する。オフライン閲覧と社内全員編集の既存方針は維持する。

## オフライン・端末保存

会社データのスナップショットと表示設定はユーザーID・会社IDで分離。オンラインで権限を確認できた予定だけを保存し、オフラインは閲覧・コピー・PDF出力に限定。再接続時は権限を再確認する。認証切れや権限拒否時にオフライン表示へ自動退避して制限を回避しない。

ログアウト時は、そのユーザーの会社スナップショットと表示設定をこのブラウザーから消去し、画面・開いていた編集画面・コピー欄も消す。別アカウント、別会社の遅れて届いた通信結果は適用しない。

認証情報とPKCE情報はログアウト操作時に通信より先に端末から削除する。保存世代を切り替えることで、別タブや遅れて返った認証更新が復活させない。サーバー側の終了は、端末へ保存しない独立したSDKで試行する。通信障害中はサーバー側の終了を保証できないが、この端末での自動ログインは防ぐ。SDKの通信終了を待たずログイン画面へ戻る。

端末内データは暗号化ストレージではない。端末・ブラウザーを使える人は保存済みデータを閲覧できる。権限停止や退会後も、切断中の端末・以前のバージョンが保存したデータ・コピー済みPDF等をサーバーから即時削除することはできない。この制約を受け入れてオフライン閲覧を維持する。

Service Workerは公開静的ファイルだけを保存する。Supabase認証セッションはSDKがブラウザーに保存し、カレンダー取り込み用トークンは従来どおりメモリーのみ。

## 検証

`npm test`にPostgreSQL互換のPGliteを使った実DBテストを含む。匿名・別会社・承認待ち・停止・セッション無効化・旧API・権限昇格・最後の管理者・同時編集を検証。PGliteは開発用で、公開ファイルには含めない。実際のGoogle OAuth同意と本番Supabaseの設定は、公開切り替え時に別途検証が必要。
