# Task workflow

## Risk and proportional work

| レベル | 例 | 必須の工程 |
| --- | --- | --- |
| L0 | 読取、質問への回答 | 必要な根拠確認。task作成は省略可 |
| L1 | 明確で小さな局所修正 | 差分と適切な検証。独立したResearch/Planは省略可 |
| L2 | 複数ファイル、機能追加 | taskとPlan。不確実性があればResearch。実装・検証・レビュー |
| L3 | 構造、認証、認可、移行、インフラ、秘密、破壊的変更 | Research、Plan、人の承認、実装、検証、レビュー |

形式を満たすために無関係な文書やテストを作らない。依頼が明示的に変更範囲を承認していれば、その承認を記録して進める。同じ範囲で確認を繰り返さない。新しい不明点・矛盾・公開範囲や破壊性の増加は確認する。

## Lifecycle

`inbox → notebook → outbox → archive`

| 所在・request.status | 意味 | 次への条件 |
| --- | --- | --- |
| inbox | 受付・未着手 | 目的・範囲を把握して着手 |
| notebook | 調査・実装中 | 必要な作業・検証・差分レビューが終わり、残件を明示 |
| outbox | エージェントの作業完了、人の確認待ち | ユーザーが結果を確認・了承 |
| archive | 確認済み | 過去記録として参照。自動削除しない |

- task ID：`TASK-YYYYMMDD-short-kebab-description`。状態が変わってもIDは維持する。
- taskフォルダごと**移動**し、requestのstatusも更新する。状態ごとにコピーを残さない。
- 修正依頼があればoutboxからnotebookへ戻す。既存結果を消さず追記・更新理由を残す。
- 状態以外の阻害要因はrequestの未解決欄へ記録する。進められない作業を完了扱いしない。
- Windowsで移動・削除する前に、解決済みの絶対パスが意図したwork内であることを確認する。

## Task contents

```text
TASK-YYYYMMDD-short-kebab-description/
├── request.md
├── research/     必要な調査と根拠
├── plans/        承認範囲・実装順序・検証
├── results/      必要な検証記録
└── handoff.md    実施結果、残件、確認ポイント
```

必要なファイルだけ作成し、[テンプレート](_templates/request.md) を用途に合わせて簡略化する。実装をtask内にコピーせず、本来のソースを変更する。

1. **Research**：コード・一次資料・実環境の事実を区別し、不確実性と推奨案を整理する。
2. **Plan**：対象、対象外、工程、検証、リスク、戻し方を記録する。承認者・日付は実際の人の承認を根拠に記録する。
3. **Implement**：承認範囲で変更。新しい問題は記録・確認し、無関係な変更を混ぜない。
4. **Verify**：意味のある検証、既存必須チェック、セキュリティ・公開範囲の確認。未実施の理由も書く。
5. **Review**：差分、仕様との整合、個人情報・秘密、検証の限界を確認してhandoffへ。

Planのstatus：draft / approved / superseded。人の承認前にapprovedへしない。ユーザーによる元の依頼が承認に当たる場合は、その具体的な範囲を根拠にする。

## Visibility and promotion

動的なtaskはGit除外。README・規則・テンプレートだけ共有する。Git除外は秘密の保管を許可するものではない。ログに秘密値・本番データを残さない。

終了時、必要な恒久仕様はdocs、判断はADR、出典付き知識はwikiへ必要部分だけ反映する。公開前に内容を確認する。MEMORYは索引として必要なリンクだけに留める。私的なtaskや原本への参照を公開PRへ自動転記しない。
